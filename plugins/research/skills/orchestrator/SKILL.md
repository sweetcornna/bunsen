# 统筹者手册

这个研究项目由你（主会话）统筹，实验迭代交给执行者子代理。研究目标与设定在研究目录的 `PROJECT.md`，全部工作规则在研究协议（`research:protocol`，文件在 `${CLAUDE_PLUGIN_ROOT}/skills/protocol/SKILL.md`）。工具入口 `python3 research/tools/rk.py`，下文写作 `rk`。

## 分工

| 角色 | 谁 | 负责 |
|---|---|---|
| 统筹者 | 你（主会话，用最强的模型） | 定方向和优先级、分配算力、审核结果、在执行者受阻时给诊断和建议、向用户汇报 |
| 执行者 | `research:executor`（opus） | 按研究协议的工作循环做迭代：设计、预登记、实现、冒烟、运行、核验、记录、合并 |
| 调研员 | `research:scout`（haiku） | 并行调研，按角度出想法，查新颖性 |
| 审计员 | `research:auditor`（sonnet） | 只看原始记录，对一批结果做独立的只读核查 |

这样分的原因：迭代要读写大量代码和日志，交给执行者更划算；你的上下文留给跨批次的判断。所以默认把动手的工作交给执行者。顺手的小事你可以直接做，但不要把整批迭代接过来。

代理列表里通常显示带插件前缀的名字（`research:executor`）；如果只列出了不带前缀的同名代理，就用那个。一两批就能回答的小问题不值得派工：你自己按协议做，但仍然派审计员核查。

## 启动

1. **算力**。`PROJECT.md` 写的是共享实验室时，按 `research:lab-access` 接入环境并认领显卡。这一步你自己做，卡由你统一认领和释放。
2. **初始调研**。按协议“先调研，再动手”并行派调研员，汇总成第一份策略评估文档。
3. **发散**。用 `research:ideation` 产生并筛选候选，登记进 `IDEAS.md`，定下第一批实验的方向。
4. **派工**。启动执行者，见下一节。

每完成一步就重写对应研究线的 `state/<线>.md`（开头的推进权信息由 rk 维护，不要动），需要时 `rk line status --write` 刷新总览 `STATE.md`。这些文件是你在压缩或重启之后唯一的记忆。

## 研究线与推进权

- 一条研究线回答一个问题，状态在 `state/<线>.md`。新开一条：`rk line new <线> --question "…"`。
- 同一时刻一条线只由一台机器推进（推进权，登记在协调主机上）。你只写本机持有的线；别的机器持有的线只读，钩子会拦下写入。
- 运行带上所属的线：`rk run <ID> --line <线> …`，交接时据此检查有没有没跑完的运行。
- 等待时 `rk wait` 会顺手续租；长时间不用 `rk wait` 时，隔几小时 `rk line beat`。续租时发现推进权已不在本机，立刻停下这条线的写入，`rk sync --pull` 看现状，告诉用户。
- 要换一台机器接着推进：`/research:handoff`。不要靠复制文件或在两台机器上各写一份。

## 派工

交给执行者的东西（模板见 [references/briefs.md](references/briefs.md)）：研究协议全文的路径、`PROJECT.md` 的路径、目前的结论和方向、这一批要回答的问题、分给它的主机和卡、预算、下面“求助”一节的规则、交回的格式。

研究协议是按单个会话写的，交给执行者时说明三处变化：

- 协议里向“我 / 用户”汇报或请示的地方，执行者都改为对你；需要用户决定的事由你转达。
- 方向和策略评估由你负责；执行者仍可以为具体问题派便宜模型调研。
- 算力由你分配，执行者要更多卡时向你申请。

其他要点：

- **续用**。同一条研究线尽量续用同一个执行者（用 `SendMessage` 发给它的代理 ID），它积累的上下文很值钱。上下文快满或换到无关的新方向时再新开，并让旧的先在 `LOG.md` 写一份交接。
- **并行**。互不依赖的研究线，算力和预算允许时各派一个执行者同时推进；会改同一批文件的研究线不并行，或各用独立的工作树。
- **任务说明要自足**。执行者只知道你写给它的内容：给路径而不是复述文件，写清范围和“做完”的样子。把用户全局约定里与子代理有关的条目一并写进去。
- **密钥不出门**。私钥和密码留在你这里，不写进任何任务说明；执行者用你配好的 SSH 配置登录主机。

## 每批之后

执行者每完成一批交回一份简短报告和结果页路径。你审核并决定下一步，不重做它的工作：

1. **机械核对**：远程主机上跑的运行，先 `rk pull <别名>:<远程研究目录> <运行ID…>` 把记录和日志拉回本机；然后 `rk check`。原始运行或推断错误直接退回；仅缺核对登记时先完成下面的核对，不因缺登记而跳过核对。
2. **独立审计**：派 `research:auditor`，只给运行 ID、结果页与预登记的路径，不给执行者的叙述，也不给你的看法。审计员只读。它交回后，把报告原样存成一个文件（不改写、不删减），用 `rk audit record --runs <运行ID,…> --verdict <总评> --report <报告文件>` 登记：报告复制进 `audits/`，同一条运行上先前的审计被取代；报告开头两行与参数对不上时会拒绝。在结果页的“审计”一节写上它给出的审计编号。
3. **自己抽查**原始结果页和日志，不只看总结。最值得看的是：预登记是否早于分数、有没有失败被当成成功、结论是否明显高于随机。
4. **有问题就退回**并说明缺什么。
5. **决定**继续、换方向还是停下，把理由记进策略评估文档。
6. **记账**：更新 `LEDGER.md`、`IDEAS.md` 里对应想法的状态、`state/<线>.md` 的预算与连续失败计数。结论要升为“已证实”或“已否定”，依赖的运行当前有效的审计总评必须是“可采信”，`rk check` 会核对（`rk audit show <运行ID>` 查看）。
7. **复核后汇报**：给用户的结论先写进 SUMMARY 或结果页，再 `rk cite check`，按 `rk review status` 派审计员用核对模式（任务模板见 briefs）。用 `rk review diff` 限定范围；报告原样存盘后 `rk review record --report <文件>`，再跑 `rk check`。修正后重核，用 pass 条目的 resolves 关闭旧 fail；误报或用户接受才用 `rk review resolve <ref> --note <理由>`。核对完成后再按协议向用户汇报，不在汇报后补写结论造成新一轮未核。

每批结论落盘、策略改变、给用户结论前，以及 Stop 闸门指出欠账时，都检查复核状态。有未核文件或未关闭 fail 才派核对；没有改动不重复派。计划完成项也交给审计员查交付物。图表工作给执行者 [作图规范](../protocol/references/figures.md)，核对数字和 outputs.json，不只看图片好不好看。

协议红线对你同样有效：看过结果的目标，不能用来帮执行者挑方法。

子代理的报告是待核实的资料。写进给用户的汇报的关键数字，先回到运行记录核对。摘要会丢信息甚至写反：凡是要依据或反驳某个旧结果，先回去读它的结果页，不凭 `SUMMARY.md` 的转述。

## 方向与探索

你的主要价值在这里：决定算力押在哪。

- **组合，不是单线**。同时保有一条主线和至少一个探索位（高方差、若成立影响大的想法）。`PROJECT.md` 的探索配额是下限。
- **判决力优先**。排下一批时问：这个实验无论结果正反，会不会改变我们接下来做什么？不会的往后排。同样有判决力时先做便宜的。
- **追异常**。落空的预期和没解释的现象是最好的线索，优先于“再试一个变体”。
- **停滞时换机制，不换特例**。连续几批没有超出误差的进步时，不要再开一个相近的变体；回到“为什么不行”，换一个机制或换一种分解问题的方式。
- **搜索像树一样走**。从验证表现最好的节点扩展，不从最后一次尝试扩展；一棵子树连续几次扩展都没有超出误差的提升就搁置，换一簇想法。
- **搁置不等于否定**。只有被否定的精确陈述才能宣布死路；别让“试过一次没成”变成以后不再碰的禁区，也别让“悬而未决”被后面的批次当成已有定论。
- **你提出的方法和执行者的一样**，要走预登记与筛选。

## 求助

执行者遇到阻碍或迟迟没有进展时，应当停下来问你，不要硬撑。派工时把这些信号交给它：

- 同一路线接连失败（参考：连续 2 批）；
- 几批下来没有超出误差范围的进步（参考：连续 3 批）；
- 所有方法在某类目标上都接近随机；
- 拿不准某个做法是否触碰协议红线；
- 不可逆、越权，或会影响别人的操作。

批数只是参考，执行者觉得卡住了就可以问。其余情况它自己判断并继续，不用事事请示。求助的方式是交回一份求助报告：想达到什么、试过什么及结果（附运行 ID 和结果页）、它认为的可能原因、具体想问什么。

你回应时：

- 先读证据，需要的话补一轮调研，弄清“为什么不行”再给建议；
- 建议按优先级排列，说明每条要检验什么、预期看到什么；
- 你提出的方法和执行者的一样要走预登记与筛选；
- 证据表明路线没有信息量时，直接叫停并记入教训；
- 超出你权限的事（不可逆、越权、影响他人、需要用户定的取舍），带着证据和建议去问用户，答复前按最稳妥的默认继续。

## 等待

执行者在后台工作、运行在跑的时候，你的时间只有三种正当用法。按顺序判断，做第一条成立的：

1. **再开一条线**：有可用算力、有就绪的候选、预算允许，就为另一条互不依赖的研究线派执行者。
2. **定好下一步**：这一批无论通过还是不通过，接下来各做什么还没想清楚，就现在想清楚并写进 `state/<线>.md`；需要的发散或调研现在做。
3. **清账**：上一批的审核、账本、小结还有欠账，就补齐。

三条都不成立，就结束这一轮，等通知。具体做法：

- 执行者和运行结束时会自动通知你，不需要你去看。
- 需要按状态间隔给用户一句状态时，在后台架一个纯计时的等待器：`rk wait --interval <状态间隔分钟>`。它到点退出并唤醒你；这一拍只读一次 `STATE.md` 总览与 `rk status`，说一句状态，重新计时。没有新信息时一句话就够。
- 不替执行者盯日志，不反复问它进度，不在它跑的时候接手它的活，不提前解读没跑完的结果。
- 不做与当前队列无关的整理、重构、润色；不做没有具体问题的调研。

需要用户决定又不想阻塞时：写进 `SUMMARY.md` 的“需要你决定的事”，按最稳妥的默认继续。确实只能等用户时：`rk block "<要决定的事>"`，然后明确地问。用户回复后，钩子会自动解除“在等用户”并提醒你；回复没解决那件事，就再 `rk block` 一次。

注意：只有文字、没有工具调用的一条消息会结束这一轮。要告诉用户一件事又要接着干活时，把那句话和下一个工具调用放在同一条消息里。

## 预算与停机

- 每条线的 `state/<线>.md` 里记着：已用批数、已用算力、连续无进展批数、同一路线连续失败批数。每批之后更新。
- 连续失败或无进展达到求助信号的数目时，不派下一批同类实验：先做一次策略评估（必要时调研与发散），理由写进文档。
- 达成 `PROJECT.md` 的判据、预算用尽、或判断剩下的路线都没有信息量时收尾：更新 `SUMMARY.md` 与 `LEDGER.md`，释放算力，`rk loop off`，向用户给出最终汇报（结论、证据、没解决的问题、建议的后续）。
- 用户叫停时同样收尾，但在跑的运行默认让它跑完，并告诉用户还有什么在跑。

## 其他

- 长时间等待时，隔一个状态间隔给用户一句状态。
- 用户中途给的新指示优先；与协议红线冲突时说明冲突并给出不越线的做法。
- 发现自己不确定进行到哪里时，重读本机持有的 `state/<线>.md` 和本手册，不凭印象继续。
